# 04. Итераторы, локальность и измерение обхода контейнеров

## Цель и объём

Сравнить последовательный обход `std::vector<std::uint64_t>` и
`std::list<std::uint64_t>` с одинаковыми значениями и подготовить
воспроизводимый отчёт. Это первый эксперимент блока `cpp-performance-lab`
из ROADMAP.md; здесь он выполняется внутри учебного репозитория.

После RAII, LRU и RingBuffer переходим к итераторам STL, ограничениям
шаблонов, инвалидированию ссылок и измерению стоимости операций.
Результат упражнения — код, исходные измерения и собственное объяснение.
Заранее заданного победителя или обязательного ускорения нет.

C++20. Ориентир — 4–6 занятий по 60–90 минут. Темп можно менять.
Существующие реализации упражнений 01–03 менять не требуется.
Многопоточность, собственные контейнеры и аллокаторы в объём не входят.

## Часть A. Контракт и предсказания до измерений

В собственном README до написания benchmark запиши:

1. Какие операции итератора нужны для полного последовательного обхода.
   Какими стандартными iterator concepts это выразить в C++20?
2. Что допустимо для итератора vector и list: `++it`, `--it`,
   `it + n`, `last - first`? Отдельно укажи сложность допустимых операций.
3. Одинакова ли асимптотика полного обхода? Какие различия в организации
   памяти могут повлиять на результат?
4. Предположение о результатах на малом и большом N.
   Какие наблюдения могли бы это предположение опровергнуть?
5. Что именно будет измерено, что останется вне измеряемого участка
   и какие факторы не контролируются.

Это твои рабочие гипотезы, а не ответы для заучивания. Сохрани их до запуска,
а затем сравни с данными.

## Часть B. Один алгоритм обхода для двух контейнеров

Самостоятельно реализуй `checksum(first, last)` в `checksum.hpp`.

Контракт:

- Вход — корректный полуинтервал итераторов одного диапазона, значения
  которого имеют тип `std::uint64_t`. Неконстантные и константные итераторы
  обоих выбранных контейнеров должны поддерживаться.
- Используй один шаблонный алгоритм; требования к итератору и типу значения
  вырази ограничениями C++20. Не требуй произвольного доступа, если алгоритму
  он не нужен.
- Результат — сумма элементов в `std::uint64_t` по модулю 2^64.
  Пустой диапазон даёт 0.
- Элементы не изменяются, контейнер не копируется.
  Алгоритм не выделяет динамическую память.
- Для N элементов алгоритм выполняет линейное число действий обхода;
  дополнительная память O(1).
- В этой части напиши цикл самостоятельно. `std::accumulate` разрешён
  как независимая проверка результата в тестах.

Напиши собственные тесты:

- пустой диапазон, один элемент, нули, несколько известных значений;
- переполнение беззнаковой суммы;
- одинаковый результат для vector и list с одинаковой последовательностью;
- константные итераторы и непустой поддиапазон;
- исходные значения после вызова не изменены;
- компиляционные проверки допустимых iterator concepts;
- неподдерживаемый тип значения отклоняется ограничением интерфейса.
  Отрицательную компиляцию держи отдельно от обычной успешной сборки.

На этом этапе получи корректный код и тесты. Измерения ещё не нужны.

## Часть C. Время жизни и инвалидирование

В README самостоятельно заполни таблицу со столбцами:
операция, какие итераторы/ссылки сохраняются, что происходит с прежним end,
источник правила.

Обязательные строки:

- vector: push_back с перераспределением и без него;
- vector: reserve, когда capacity действительно увеличивается;
- vector: erase одного элемента;
- list: вставка и erase одного элемента.

Для случаев, где сохранность гарантирована, напиши небольшой корректный
тест. Для случая перераспределения vector сначала обеспечь указанное
условие через size/capacity; не полагайся на конкретный коэффициент роста.
Инвалидированные итераторы, указатели и ссылки не разыменовывай,
не сравнивай и не используй для демонстрации ошибки.
Отсутствие сообщения санитайзера не является проверкой сохранности.

Не требуется писать готовый теоретический конспект. Достаточно собственной
таблицы, ссылок и объяснения нескольких примеров на защите.
Личные заметки остаются недоступны агентам по AGENTS.md.

## Часть D. Эксперимент

Используй Google Benchmark. Подключение зависимости и отдельных CMake-целей
можно поручить локальному Codex после появления собственных исходников.
Версию или commit зависимости зафиксируй; плавающая ветка не подходит
для воспроизведения результатов.

### Данные и сравниваемая работа

- Обязательные N: 1024, 32768, 1048576.
- Значения генерируются во время исполнения с фиксированным seed
  `0xC0FFEE`. Алгоритм генерации и диапазон значений опиши в README.
- Для каждого N два контейнера содержат одну и ту же последовательность.
  До измерений проверь совпадение checksum с независимым результатом.
- Сравнивается один полный проход checksum по уже созданному контейнеру.
  Создание, заполнение, уничтожение, генерация данных, проверка результата
  и вывод на экран находятся вне измеряемого участка.
- Каждый измеряемый повтор действительно обходит N элементов.
  Не измеряй повторное использование заранее вычисленной суммы.
- Контейнер повторно используется между проходами.
  Укажи, как выполнялся прогрев; не называй такой опыт измерением
  гарантированно холодного кеша.
- Основной опыт однопоточный. Порядок запуска вариантов чередуй
  или используй перемешивание повторений и запиши выбранный способ.

### Оптимизатор и сборка

- Измеряй отдельную Release-сборку с оптимизацией, без санитайзеров
  и отладочных итераторов STL. Для обоих вариантов используй одинаковые флаги.
- Обеспечь наблюдаемое использование результата каждого прохода
  средствами Google Benchmark. Изучи ограничения DoNotOptimize:
  одного наличия этого вызова недостаточно для доказательства,
  что нужная работа осталась внутри измеряемого повтора.
- Не ставь барьер на каждый элемент: в этом опыте сравнивается обычный
  оптимизируемый обход, включая допустимую оптимизацию vector.
- Проверь дизассемблирование итогового Release-бинарника для обоих
  вариантов: где находится обход, остаётся ли он внутри повтора.
  Запиши команду и краткое наблюдение. Полный разбор ассемблера не нужен.
- Отдельно запусти тесты корректности в Debug с предупреждениями
  и доступными ASan/UBSan. Диагностические запуски не включай в CSV времени.

### Повторения и исходные данные

Для каждой пары (контейнер, N) — минимум 7 повторений benchmark.
Настрой длительность, достаточную для устойчивого измерения;
начни с минимального времени 0.2 секунды на повторение.
Не выбирай единственный лучший запуск.

Сохрани исходные результаты всех повторений в `results/raw.csv`.
В отчёте для каждой пары приведи N, медиану времени полного прохода,
разброс (например, минимум/максимум) и время на элемент.
Явно укажи выбранную колонку времени и единицы.
Один проход обрабатывает N элементов; учти это при нормировке.
Агрегированные строки Google Benchmark не считай отдельными повторениями.

Зафиксируй CPU, ОС, компилятор, стандартную библиотеку, флаги, build type,
версию Google Benchmark, seed и команды воспроизведения.
Сообщи о существенной фоновой нагрузке или ограничениях виртуальной среды.
Аппаратные perf counters полезны, но необязательны.

## Часть E. Собственный отчёт и защита

В README на 1–2 страницы добавь:

1. Первоначальные гипотезы и таблицу фактических измерений.
2. Объяснение наблюдаемой разницы. Разделяй измеренный факт
   и гипотезу о причине; без counters не объявляй число cache misses измеренным.
3. Что ограничивает выводы: тип элементов, N, размещение узлов list,
   повторный обход тех же данных, компилятор и аппаратная среда.
4. Почему этот опыт сам по себе не отвечает на вопрос,
   какой контейнер выбрать для произвольной задачи.
5. Один следующий эксперимент, который мог бы проверить твоё объяснение.
   Выполнять его для завершения упражнения необязательно.

На защите объясни:

- ограничения шаблона и необходимые операции итератора;
- отличие стоимости поиска позиции от стоимости вставки по готовому итератору;
- один пример корректного и один пример запрещённого использования
  сохранённого итератора после изменения контейнера;
- что именно измерялось и как исключено удаление обхода оптимизатором;
- какие выводы подтверждаются данными и что пока остаётся предположением.

## Файлы и критерии завершения

Ожидаемые результаты, которые студент создаёт самостоятельно:

- `checksum.hpp` — алгоритм;
- `tests.cpp` — проверки;
- `benchmark.cpp` — два сравнимых benchmark;
- `README.md` — контракт, гипотезы, таблица инвалидирования и отчёт;
- `results/raw.csv` — реальные исходные измерения;
- `current/CURRENT-04.md` — команды, результаты, нерешённые вопросы.

Только TASK.md и начальный прогресс добавляются при выдаче задания.
Реализацию, тесты, измерения и отчёт агент заранее не создаёт.

Готовность: корректность проверена, выполнены требования к эксперименту,
другой человек может повторить запуск по README, а студент самостоятельно
объясняет результат и его ограничения. Любая величина относительной скорости,
включая отсутствие устойчивой разницы, допустима при честном измерении.

Первый шаг: часть A, затем checksum и несколько небольших тестов.
Начинай benchmark после проверки корректности.
