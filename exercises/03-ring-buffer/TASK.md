# 03. Ограниченный кольцевой буфер

## Цель и объём

Реализовать однопоточный FIFO-контейнер `RingBuffer<T>` фиксированной вместимости.
Он станет основой для последующих упражнений с очередями сообщений и feed handler.

Новые темы: шаблонный класс, ограничения на тип, perfect forwarding, раздельное
время жизни хранилища и элементов, перемещение и гарантии исключений.

C++20. Ориентир — 4–6 занятий по 60–90 минут. Это оценка, а не срок сдачи.
Задание самостоятельно: реализацию LRU менять или повторно проверять для него не требуется.
Незавершённые проверки LRU остаются записанными в `current/CURRENT-02.md`.

## Модель контейнера

Буфер принимает элементы в конец и извлекает из начала. Порядок — FIFO.
Вместимость неизменна после конструктора; при переполнении элементы не вытесняются:
операция добавления сообщает об отказе.

Однажды выделенное хранилище переиспользуется по кругу. Сам буфер выделяет
хранилище в конструкторе и не расширяет его в операциях добавления и извлечения.
Элементы T могут самостоятельно выделять память; это отдельная стоимость.

Нельзя реализовывать контейнер через `std::queue`, `std::deque` или `std::list`,
сдвигать все элементы при извлечении или увеличивать фактическое число ячеек.
Стандартные средства управления временем жизни разрешены; ручные аллокаторы,
placement new и арифметика сырых указателей не обязательны.

## Поддерживаемые типы

- T — неконстантный, не volatile объектный тип, не массив.
- Конструктор перемещения и деструктор T не бросают исключений.
- Конструктор по умолчанию и копирование T не требуются.
- Тип, не удовлетворяющий ограничениям, должен отклоняться при компиляции
  с понятной диагностикой.
- Для этой версии сам RingBuffer нельзя копировать или перемещать.

Поддержка произвольного бросающего move, аллокаторов и многопоточности
в объём упражнения не входит.

## Публичный интерфейс

Это контракт интерфейса, не реализация. Собственные необходимые include
и способ проверки ограничений выбери самостоятельно.

```cpp
template<class T>
class RingBuffer {
public:
    explicit RingBuffer(std::size_t capacity);

    RingBuffer(const RingBuffer&) = delete;
    RingBuffer& operator=(const RingBuffer&) = delete;
    RingBuffer(RingBuffer&&) = delete;
    RingBuffer& operator=(RingBuffer&&) = delete;

    bool try_push(const T& value)
        requires std::is_copy_constructible_v<T>;

    bool try_push(T&& value);

    template<class... Args>
    bool try_emplace(Args&&... args)
        requires std::is_constructible_v<T, Args...>;

    std::optional<T> try_pop() noexcept;

    T& front();
    const T& front() const;

    void clear() noexcept;

    std::size_t size() const noexcept;
    std::size_t capacity() const noexcept;
    bool empty() const noexcept;
    bool full() const noexcept;
};
```

При корректном завершении жизни буфера все принадлежащие ему живые элементы
уничтожаются. Явный пользовательский деструктор не обязателен: выбор
автоматического управления ресурсами допустим.

## Точный контракт

### Создание и состояния

- После конструктора элементов нет; capacity равна переданному числу.
- `size() <= capacity()` после любой завершившейся операции.
- `empty()` равносильно `size() == 0`.
- `full()` равносильно `size() == capacity()`.
- Вместимость 0 допустима. Такой буфер одновременно empty и full.
- Создание буфера не создаёт объектов T для всех свободных ячеек.
- После каждого удаления объект извлечённого элемента в ячейке уничтожен;
  свободная ячейка не должна держать старый живой T до следующей вставки.

### Добавление

- При наличии места `try_push` сохраняет элемент в конце и возвращает true.
  Перегрузка const T& копирует, перегрузка T&& перемещает.
- `try_emplace` создаёт элемент из переданных аргументов и возвращает true.
  Она должна поддерживать perfect forwarding и не требовать
  предварительно созданного временного T.
- При полном буфере все три операции возвращают false: порядок, элементы
  и размер не меняются, сохранённый T не создаётся.
- При отказе из-за переполнения `try_push(std::move(value))` не забирает
  ресурс у value.
- Аргументы функции вычисляются обычным образом до её вызова. Условие
  о переполнении не отменяет побочные эффекты вычисления аргументов.
- Для этого упражнения аргументы добавления не должны ссылаться
  на элементы самого буфера. Обработку такого самоалиасинга не требуем.

### Доступ и извлечение

- `front()` возвращает ссылку на первый элемент без изменения порядка.
  Для пустого буфера обе перегрузки бросают `std::out_of_range`.
- `try_pop()` возвращает std::nullopt, если буфер пуст.
- При успехе `try_pop()` передаёт первый элемент возвращаемому optional,
  удаляет соответствующий элемент из буфера и уменьшает размер.
- Элемент, возвращённый `try_pop`, принадлежит вызывающему коду
  и живёт независимо от буфера.
- `clear()` уничтожает все сохранённые элементы, делает size равным 0
  и сохраняет capacity. После clear буфер можно снова использовать.
- Константный объект предоставляет только константный доступ к front.

### Заимствованные ссылки

Ссылка из front действительна, пока соответствующий элемент живёт в ячейке.
Добавление других элементов не инвалидирует её. Извлечение этого элемента,
clear и уничтожение буфера инвалидируют ссылку.

Повторное использование той же ячейки не разрешает читать старую ссылку
по контракту контейнера. В тестах нельзя разыменовывать ссылку после
инвалидирования. Изменение состояния T через разрешённую неконстантную
ссылку не меняет порядок FIFO.

### Исключения

- Конструктор буфера может бросить при выделении хранилища.
- Копирование T и конструирование T из аргументов могут бросать.
  В таком случае добавление не меняет размер, порядок и существующие
  элементы и не оставляет лишний живой T в свободной ячейке.
- Побочные эффекты пользовательского конструктора вне буфера
  откатывать не требуется.
- При наших ограничениях на T, `try_pop` и `clear` не бросают.
  Обоснуй спецификации noexcept в README.
- После исключения буфер остаётся пригодным для последующих операций.
  Ошибку создания T не превращай в false: исключение передаётся вызывающему коду.

### Сложность

Проверки состояния, front и управление ячейками при добавлении/извлечении
должны занимать O(1) по capacity. Стоимость конструктора, копирования,
перемещения и уничтожения T учитывай отдельно.
Clear — O(size) вызовов уничтожения; память — O(capacity).

## Контрольная последовательность

Вместимость 3:

| Операция | Результат | Содержимое от первого к последнему |
|---|---|---|
| try_push(10) | true | 10 |
| try_push(20) | true | 10, 20 |
| try_push(30) | true | 10, 20, 30 |
| try_push(40) | false | 10, 20, 30 |
| try_pop() | 10 | 20, 30 |
| try_pop() | 20 | 30 |
| try_push(40) | true | 30, 40 |
| try_push(50) | true | 30, 40, 50 |
| clear() | size = 0 | пусто |
| try_push(60) | true | 60 |

Повтори несколько циклов заполнения и освобождения: переход через
физический конец хранилища должен сохранять порядок FIFO.

## Теоретические блоки: подготовь самостоятельно

До основной реализации выбери по одному блоку для самостоятельной записи
и передачи наставнику на проверку:

1. Шаблон класса: требования к T, проверка допустимости операций,
   отличие ошибки ограничения от ошибки внутри тела функции.
2. const T&, T&& и forwarding reference: какие аргументы принимает
   каждая форма, какие категории выражений нужно сохранить при emplace.
3. Время жизни хранилища и T: чем свободная ячейка отличается от живого
   элемента, какие операции начинают и заканчивают его жизнь.
4. Владение после перемещения: что принадлежит буферу, входному объекту
   и результату pop; почему отказ при переполнении не забирает ресурс.
5. Гарантия исключений и noexcept: что остаётся истинным после
   неудачного добавления и на какие требования к T опирается pop.

Это список заданий для изучения, а не готовый конспект. Наставник проверяет
только явно переданный в диалог блок: ошибки, пропущенные условия,
необоснованные утверждения и ответы на вопросы. Готовую теорию,
доказательства и исправленный текст не выдаёт.

Личные `notes/therory/` и `notes/theory/` агенты не читают и не изменяют.
В прогресс попадают только название темы и результат проверки.
Не требуется передавать все заметки для перехода к практике: передавай
только выбранные фрагменты в своём темпе.

## Обязательные проверки

### Поведение FIFO

- Пустой буфер: размер, признаки, nullopt; обе front бросают.
- Вместимости 0, 1, 2 и 3.
- Переполнение не меняет данные, порядок и размер.
- Многократный обход кольца с чередованием push/pop.
- Успешный и повторный clear; использование после clear.
- Отдельный разбор full/empty при нулевой вместимости.
- Ссылка front остаётся действительной после добавления других элементов.

### Типы и владение

- int и std::string.
- Move-only тип, например std::unique_ptr<int>; успешная передача владения.
- Переполнение с move-only аргументом сохраняет ресурс входного объекта.
- Тип без конструктора по умолчанию.
- Тестовый тип со счётчиком живых экземпляров: создание пустого буфера,
  emplace, pop, clear, уничтожение буфера. Учитывай отдельно живые
  входные объекты и возвращённый optional.
- Компиляционная проверка, что const front возвращает const T&,
  а сам буфер не копируется и не перемещается.
- Компиляционные отрицательные проверки неподдерживаемого T держи
  отдельно от обычной успешной сборки и опиши способ их запуска.

### Отказы

Создай тестовый тип с noexcept move и деструктором, но управляемым
исключением из обычного или copy-конструктора.

Проверь неудачное emplace и копирующий push: состояние буфера не меняется,
лишних живых объектов нет, последующая успешная вставка работает.
Отдельно проверь, что при полном буфере конструирование сохранённого T
не запускается. Для этого не обязательно перехватывать глобальный new.

### Независимая модель

Для int разрешена эталонная std::deque. Она используется только в тестах.
На фиксированном seed сравни последовательности push/pop/clear/front
при нескольких малых вместимостях. Сравни возвращённые результаты,
размер и состояние; печатай seed и операции при несовпадении.
Сначала реализуй перечисленные сценарии, затем добавляй генератор.
