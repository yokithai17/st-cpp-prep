# 01. Владение файловым дескриптором

Начинать после диагностики. Ожидаемый объём: 2–3 занятия по 60–90 минут, с корректировкой по уровню. Практика предназначена для Linux/POSIX.

## Задача

Реализовать `UniqueFd` — объект, единолично владеющий файловым дескриптором. Дескриптор — целое число; значение `-1` обозначает отсутствие владения. Обёртка принимает владение уже открытым дескриптором.

## Требуемое поведение

- Default construction создаёт пустой объект.
- Copy constructor и copy assignment запрещены.
- Move constructor и move assignment передают владение; источник становится пустым.
- При move assignment прежний ресурс назначения освобождается; self-move не вызывает повторного закрытия.
- Destructor освобождает принадлежащий ресурс и не бросает исключений.
- `get()` возвращает номер без передачи владения.
- `release()` передаёт номер вызывающему коду и оставляет объект пустым.
- `reset(new_fd = -1)` освобождает прежний ресурс и принимает новый. Отдельно определить поведение `reset(get())`.
- Move operations должны быть `noexcept`; инвариант владения описан в README упражнения.

Политика ошибок `close` фиксируется отдельно: не делать слепое повторное закрытие того же числового fd. Номер может быть переиспользован ОС. Перед реализацией обсудим нужные системные гарантии и ограничения.

## Проверки

Compile-time: запрет copy и поддержка noexcept move. Runtime: пустой объект, уничтожение, move construction, move assignment с уже открытым ресурсом, release/reset и self-move. Использовать реальные временные файлы или pipe; тесты не должны зависеть от конкретного номера fd и порядка открытий других процессов.

### Как писать тесты

Для этого упражнения сторонний фреймворк не нужен. Создай `tests.cpp` рядом с `unique_fd.hpp`. Это обычная C++20-программа с `main`: успешный запуск возвращает 0, неудачная проверка печатает понятное сообщение в `std::cerr` и возвращает 1. Можно начать с последовательных проверок в main, затем выделить отдельные сценарии в функции. Не используй `assert` как единственный механизм проверки: в сборке с `NDEBUG` такие проверки отключаются.

Нужные заголовки:

- `"unique_fd.hpp"` — проверяемый класс;
- `<iostream>` — сообщения об ошибках;
- `<type_traits>` — `static_assert` и traits запрета copy / noexcept move;
- `<utility>` — `std::move`;
- `<unistd.h>` — `pipe` и `close`;
- `<fcntl.h>` — `fcntl` и `F_GETFD`;
- `<cerrno>` — `errno` и `EBADF`.

Для каждого runtime-сценария подготовь ресурс, выполни одно проверяемое действие, затем проверь состояние объекта и ресурса. `pipe` создаёт два открытых fd и возвращает 0 при успехе; его ошибку обязательно обрабатывай. Передавай обёртке один конец pipe, а второй закрывай отдельно. После release закрытие переданного наружу fd становится ответственностью теста.

Открытость fd можно проверить вызовом `fcntl(fd, F_GETFD)`: неотрицательный результат означает, что fd открыт. Для проверки закрытого fd установи `errno = 0`, вызови `fcntl`, затем сразу проверь результат `-1` и `errno == EBADF`. Между закрытием проверяемого fd и этой проверкой не открывай новые ресурсы: номер может быть переиспользован. Номер fd всегда получай от ОС, не ожидай заранее 3, 7 или другое конкретное значение.

Начни с пустого объекта и закрытия ресурса деструктором. Для проверки деструктора помести обёртку во вложенную область видимости, сохрани номер снаружи и проверь его после выхода из этой области. Затем добавляй остальные сценарии из списка выше. Compile-time проверки оформляй через `static_assert` вне main.

Пока тесты не подключены к CMake, из корня репозитория:

```bash
g++ -std=c++20 -Wall -Wextra -Wpedantic exercises/01-unique-fd/tests.cpp -o /tmp/st-cpp-prep-unique-fd-tests
/tmp/st-cpp-prep-unique-fd-tests
```

После появления тестов подключим их к CMake/CTest.

Сначала описать ownership, затем написать свою реализацию, затем тесты. Готового решения в стартере нет. Задание закрыто, когда код проверен и автор может объяснить каждый переход владения.
