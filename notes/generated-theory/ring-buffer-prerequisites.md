## 1. Шаблон класса и конкретный тип

Шаблон описывает семейство сущностей. `Label<int>` и `Label<std::string>` — разные типы, полученные из одного шаблона; параметр `T` обозначает тип, а не переменную времени выполнения.

```cpp
#include <utility>

template<class T>
class Label {
public:
    explicit Label(T value) : value_(std::move(value)) {}
    const T& get() const { return value_; }

private:
    T value_;
};
```

`class T` и `typename T` в списке параметров шаблона означают одно и то же. Слово `class` здесь не требует, чтобы аргумент был пользовательским классом: `int` тоже подходит. Другие употребления `typename` имеют отдельные правила.

У метода шаблонного класса может быть собственный шаблонный параметр:

```cpp
template<class T>
struct Inspector {
    void inspect(const T& value);  // обычный метод конкретного Inspector<T>

    template<class U>
    void compare(const U& other); // шаблон метода
};
```

После выбора `Inspector<int>` параметр `T` уже известен. Параметр `U` у `compare` может выводиться заново для каждого вызова. Два уровня параметров понадобятся при чтении интерфейса с вариадическим методом.

Источник: N4861, [Templates — `[temp.pre]`](https://timsong-cpp.github.io/cppwp/n4861/temp.pre).

### Почему определения обычно помещают в заголовок

При обычном неявном инстанцировании компилятору нужно доступное определение того шаблонного кода, который требуется получить для конкретных типов. Одного объявления метода в `.hpp` и его определения в независимо компилируемом `.cpp` обычно недостаточно для произвольных аргументов шаблона. Типичный результат такого разделения — ошибка линковки при использовании неподготовленной специализации.

Поэтому обычный способ для небольшого обобщённого компонента — определения в `.hpp` либо в подключаемом им файле `.tpp`. Расширение само по себе ничего не меняет: важна доступность определения. Альтернатива — явное инстанцирование в `.cpp` для заранее выбранного набора типов. Оно требует отдельного управления этим набором и плохо подходит для открытого семейства пользовательских типов. Правила: [Implicit instantiation — `[temp.inst]`](https://timsong-cpp.github.io/cppwp/n4861/temp.inst) и [Explicit instantiation — `[temp.explicit]`](https://timsong-cpp.github.io/cppwp/n4861/temp.explicit).

Внешнее определение шаблонного метода содержит два списка параметров:

```cpp
template<class T>
template<class U>
void Inspector<T>::compare(const U& other) {
    (void)other;
}
```

Первый относится к классу, второй — к методу. Определения одного шаблона, включённые в разные единицы трансляции, должны соблюдать правило одного определения; заголовок не даёт разрешения на различающиеся версии. См. [One-definition rule — `[basic.def.odr]`](https://timsong-cpp.github.io/cppwp/n4861/basic.def.odr).

## 2. Требования к типу: какие операции действительно нужны

Обобщённый компонент должен требовать именно используемые возможности. Конструирование, присваивание, сравнение и создание по умолчанию — независимые операции. Например, можно разрешить создание из целого числа и перемещение, запретив копирование и оба присваивания. Такой тип нельзя отвергать только потому, что с ним неудобен выбранный вспомогательный приём.

`<type_traits>` предоставляет предикаты времени компиляции. Суффикс `_v` даёт логическое значение; это не вызов операции над реальным объектом. Обзор средств: [Microsoft Learn, `<type_traits>`](https://learn.microsoft.com/en-us/cpp/standard-library/type-traits?view=msvc-170).

| Средство | На какой вопрос отвечает |
|---|---|
| `std::is_object_v<U>` | Является ли `U` объектным типом? |
| `std::is_array_v<U>` | Является ли `U` встроенным массивом? |
| `std::is_const_v<U>` | Имеет ли сам `U` квалификатор `const`? |
| `std::is_volatile_v<U>` | Имеет ли сам `U` квалификатор `volatile`? |
| `std::is_constructible_v<U, A...>` | Допустимо ли прямое конструирование `U` с аргументами этих типов? |
| `std::is_copy_constructible_v<U>` | Допустимо ли конструирование `U` из `const U&`? |
| `std::is_nothrow_move_constructible_v<U>` | Допустимо ли конструирование из `U&&` без потенциального исключения? |
| `std::is_nothrow_destructible_v<U>` | Допустимо ли уничтожение без потенциального исключения? |

Классификация типов: N4861, [`[meta.unary.cat]`](https://timsong-cpp.github.io/cppwp/n4861/meta.unary.cat), [`[meta.unary.comp]`](https://timsong-cpp.github.io/cppwp/n4861/meta.unary.comp). Свойства операций и их предусловия: [`[meta.unary.prop]`](https://timsong-cpp.github.io/cppwp/n4861/meta.unary.prop).

Массив — объектный тип; проверка `is_object` сама его не исключает. Ссылка и `void` объектными типами не являются. `std::array<int, 3>` — класс, а не встроенный массив `int[3]`. Проверка `is_const_v<int*>` говорит о самом указателе, а не о том, можно ли менять объект по нему.

Свойства конструирования проверяют допустимость выражений, а не наличие функции с определённым названием. Тип, имеющий только доступный `U(const U&) noexcept`, иногда допускает создание из `U&&` через копирование. Поэтому истинный move-trait сам по себе не доказывает передачу ресурса.

Не применяй traits конструирования и уничтожения к произвольному неполному классу: у них есть требования полноты. Предварительное объявление `struct Pending;` ещё не даёт всей информации об операциях `Pending`. Диагностику недопустимых аргументов нужно проектировать с учётом предусловий самих проверок.

Именованный concept может объединять требования. Однако `std::movable` включает также присваивание и обмен, а `std::copyable` — дополнительные формы присваивания. Они не взаимозаменяемы с отдельным trait конструктора. Правила стандартных concepts: [Object concepts — `[concepts.object]`](https://timsong-cpp.github.io/cppwp/n4861/concepts.object).

## 3. Ограничение объявления и ошибка в теле

`requires` в C++20 позволяет ограничить допустимые специализации или участие функции в выборе перегрузки:

```cpp
#include <type_traits>

template<class T>
struct Copier {
    T duplicate(const T& source) const
        requires std::is_copy_constructible_v<T>
    {
        return T(source);
    }
};
```

Условие относится к конкретному методу. Оно не требует копируемости для всех остальных операций класса. Если ограничение метода не выполнено, этот метод не становится подходящим кандидатом для вызова.

`static_assert` в теле метода устроен иначе: он диагностирует проблему, когда требуется инстанцирование соответствующего тела, но сам по себе не исключает функцию из набора подходящих перегрузок. `static_assert` в определении класса может давать общую диагностику требований класса при его инстанцировании. Выбор места проверки влияет на момент и смысл ошибки. См. [Template constraints — `[temp.constr]`](https://timsong-cpp.github.io/cppwp/n4861/temp.constr).

Есть два разных употребления `requires`:

```cpp
template<class U>
concept HasSize = requires(const U& value) {
    value.size();
};

template<class U>
    requires HasSize<U>
void examine_size(const U& value) {
    (void)value.size();
}
```

`requires(...) { ... }` — **requires-expression**, выражение типа `bool`, описывающее проверяемые требования. `requires HasSize<U>` — **requires-clause**, ограничение объявления. В первом фрагменте `value.size()` не выполняется: проверяется его допустимость. Эта короткая проверка не требует конкретного типа результата и ничего не говорит о сложности `size()`.

Не считай requires-expression универсальным перехватчиком ошибок компиляции. Ошибки, возникающие глубже при инстанцировании чужих тел, могут оставаться обычными ошибками; некорректное выражение вне шаблонного объявления тоже не превращается автоматически в `false`. Источник: [Requires expressions — `[expr.prim.req]`](https://timsong-cpp.github.io/cppwp/n4861/expr.prim.req).

## 4. `const`, ссылки и категории выражений

### Доступ к объекту и его владение

Ссылка — способ обратиться к существующей сущности. Привязка ссылочного параметра сама не создаёт копию объекта и не передаёт владение ресурсом. После инициализации ссылку нельзя перепривязать: присваивание через неё присваивает значение её объекту.

Для обычного объектного типа `U`, без `volatile`, наследования и пользовательских преобразований:

| Параметр | Неконстантный lvalue `u` | Константный lvalue `cu` | Неконстантный rvalue |
|---|---|---|---|
| `U&` | да | нет | нет |
| `const U&` | да | да | да |
| `U&&`, где `U` уже задан | нет | нет | да |

`const U&` разрешает только константный доступ через эту ссылку. Он не превращает исходный неконстантный объект в константный для всех остальных путей доступа и не обещает глубокую неизменяемость ресурсов, доступных через указатели внутри `U`. Для const-rvalue обычная ссылка `U&&` тоже не подходит; `const U&` подходит. Правила привязки: [References — `[dcl.init.ref]`](https://timsong-cpp.github.io/cppwp/n4861/dcl.init.ref).

### Категория принадлежит выражению

В C++20 различают три основные категории:

- **lvalue** — например, выражение, называющее обычную переменную;
- **xvalue** — выражение, обозначающее объект как пригодный для переиспользования ресурсов, например `std::move(s)`;
- **prvalue** — например, `42` или `std::string("abc")`, участвующее в вычислении значения или инициализации результата.

`rvalue` объединяет prvalue и xvalue; `glvalue` объединяет lvalue и xvalue. Тип выражения и его категория — разные характеристики. У выражения `s` тип `std::string`, но оно lvalue. Переменная может быть объявлена как rvalue reference, а выражение с её именем всё равно будет lvalue:

```cpp
#include <string>
#include <utility>

std::string text = "draft";
std::string&& alias = std::move(text);
// alias — lvalue-выражение; std::move(alias) — xvalue-выражение.
```

Здесь не создана вторая строка: `alias` ссылается на `text`. Классификацию нельзя надёжно заменить правилом «есть имя / нет имени»: существуют и другие lvalue-выражения, например `*pointer`. Источник: [Value category — `[basic.lval]`](https://timsong-cpp.github.io/cppwp/n4861/basic.lval).

### `const` после скобок метода

`const` у метода относится к пути доступа через объект вызова. Он не означает, что результат обязательно возвращается по значению:

```cpp
struct Gauge {
    int reading = 0;
    int& value() { return reading; }
    const int& value() const { return reading; }
};
```

У константного `Gauge` доступна вторая перегрузка; у обычного объекта для такого вызова выбирается первая. Сам компилятор не обеспечивает глубокую константность объектов, достижимых через владеющий указатель-член: интерфейс класса должен учитывать это отдельно. Источник: [Non-static member functions и `this` — `[class.mfct.non-static]`](https://timsong-cpp.github.io/cppwp/n4861/class.mfct.non-static).

## 5. Две разные роли `T&&`

Посмотри на объявления, не подставляя реализацию упражнения:

```cpp
template<class T>
struct Receiver {
    void take(T&& value);

    template<class U>
    void inspect(U&& value);
};
```

Для `Receiver<std::string>` параметр `take` — `std::string&&`. `T` уже выбран вместе с классом; при вызове `take` он не выводится заново. Это обычная rvalue reference, не forwarding reference.

У `inspect` параметр `U` выводится из аргумента вызова. Форма `U&&` с выводимым неквалифицированным параметром типа здесь является **forwarding reference**. Для lvalue выводится ссылочный `U`; для rvalue — нессылочный `U`.

| Аргумент `inspect` | Выведенный `U` | Тип параметра после свёртки |
|---|---|---|
| `s`, где `s` — обычная строка | `std::string&` | `std::string&` |
| `cs`, где `cs` — const-строка | `const std::string&` | `const std::string&` |
| `std::move(s)` | `std::string` | `std::string&&` |
| `std::move(cs)` | `const std::string` | `const std::string&&` |

Форма `const U&&` не является forwarding reference. Явное задание аргумента шаблона вместо его вывода тоже меняет рассуждение о привязке. Источник: [Deducing template arguments from a function call — `[temp.deduct.call]`](https://timsong-cpp.github.io/cppwp/n4861/temp.deduct.call).

### Свёртка ссылок

Подстановки через параметры шаблонов и псевдонимы могут привести к сочетаниям ссылок. Прямо писать тип «ссылка на ссылку» нельзя; результирующий тип определяется правилами свёртки:

| Сочетание при подстановке | Результат |
|---|---|
| `U&` + `&` | `U&` |
| `U&` + `&&` | `U&` |
| `U&&` + `&` | `U&` |
| `U&&` + `&&` | `U&&` |

Например, при выводе `U = std::string&` форма параметра `U&&` становится `std::string&`. Это не специальная перегрузка, написанная вручную: работает общее правило языка. Источник: [References — `[dcl.ref]`, p6](https://timsong-cpp.github.io/cppwp/n4861/dcl.ref#6).

## 6. `std::move`, `std::forward` и пакет аргументов

### Разрешить перемещение — ещё не переместить

`std::move` из `<utility>` выполняет приведение к rvalue reference с удалением ссылочности исходного типа. Для обычного объекта результат — xvalue. Сам `move` не выделяет память, не вызывает конструктор перемещения и не меняет значение объекта. Изменение может произойти, когда результат используют для конструирования или присваивания.

```cpp
#include <memory>
#include <utility>

auto owner = std::make_unique<int>(17);
auto&& permission = std::move(owner); // только привязка ссылки
auto next = std::move(permission);   // здесь создаётся новый unique_ptr
```

В первой строке с `permission` ресурс по-прежнему принадлежит `owner`. При создании `next` выбирается перемещение `unique_ptr`.

`std::move` сохраняет `const`: из const-строки получается `const std::string&&`, которое не подходит обычному перемещающему конструктору `std::string(std::string&&)`. При создании строки из такого выражения обычно выбирается копирование из `const std::string&`. У move-only типа подходящей копирующей альтернативы может не быть вообще. Правило преобразования: N4861, [Forward/move helpers — `[forward]`](https://timsong-cpp.github.io/cppwp/n4861/forward).

### Передать категорию дальше

Имя параметра `arg` внутри функции — lvalue-выражение независимо от того, с чем параметр был связан. Обычный вызов `destination(arg)` теряет информацию о том, что вызывающий код передал rvalue.

```cpp
#include <utility>

void mark(int&) {}
void mark(int&&) {}

template<class U>
void relay(U&& arg) {
    mark(std::forward<U>(arg));
}
```

При вызове `relay(n)` для целого lvalue выбирается `mark(int&)`; при `relay(7)` — `mark(int&&)`. `forward<U>` использует **тот `U`, который вывелся у внешней функции**. Он оставляет lvalue как lvalue и даёт rvalue-путь для соответствующего исходного аргумента. Вместо безусловного `move` это позволяет сохранить намерение вызывающего кода. Сам `forward` тоже только приводит тип.

Источник с отдельным объяснением: [Microsoft Learn, `<utility>` functions, раздел `forward`](https://learn.microsoft.com/en-us/cpp/standard-library/utility-functions?view=msvc-170#forward).

### Несколько независимо выводимых аргументов

`template<class... Args>` объявляет пакет типов. `Args&&... args` — пакет параметров, каждый со своим выводом типа и категорией. Выражение `std::forward<Args>(args)...` разворачивает попарное применение `forward` ко всем аргументам. При нуле аргументов пакет пуст.

Пример общего конструирующего посредника, не контейнера:

```cpp
#include <type_traits>
#include <utility>

template<class Product, class... Args>
    requires std::is_constructible_v<Product, Args...>
Product build(Args&&... args) {
    return Product(std::forward<Args>(args)...);
}
```

Здесь `Product` задаётся явно, а типы `Args` выводятся. Проверка `is_constructible_v<Product, Args...>` согласуется с выводом forwarding references: ссылочность lvalue уже содержится в выведенном `Args`, а для нессылочного `A` проверяется аргумент категории rvalue. См. правила пакетов и вывода в [`[temp.deduct.call]`](https://timsong-cpp.github.io/cppwp/n4861/temp.deduct.call) и конструирования в [`[meta.unary.prop]`](https://timsong-cpp.github.io/cppwp/n4861/meta.unary.prop).

Не заменяй механически круглые скобки фигурными: `U(args...)` и `U{args...}` могут выбирать разные конструкторы, особенно при наличии `initializer_list`, и различаются правилами сужения. Безымянный список `{1, 2}` также не даёт обычного вывода типа для произвольного forwarding-параметра. Правила списков: [List-initialization — `[dcl.init.list]`](https://timsong-cpp.github.io/cppwp/n4861/dcl.init.list).

Perfect forwarding не продлевает автоматически жизнь аргументов и не гарантирует отсутствие копирования внутри выбранного конструктора. Если конструируемый тип сохраняет ссылку, вопрос времени жизни исходного объекта остаётся за его контрактом.

## 7. Move-only типы, RAII и передача владения

RAII связывает освобождение ресурса с уничтожением объекта-владельца. Ресурсом может быть память, файловый дескриптор или другое состояние, требующее парного освобождения. Ссылка и сырой указатель сами по себе такой обязанности не выражают.

`std::unique_ptr<int>` владеет динамическим `int`, запрещает копирование и поддерживает передачу владения перемещением. Создание нового владельца из `std::move(source)` передаёт указатель; исходный `unique_ptr` после такого перемещения пуст. Уничтожение нового владельца освобождает объект при обычном deleter. Источник: [Class template `unique_ptr` — `[unique.ptr]`](https://timsong-cpp.github.io/cppwp/n4861/unique.ptr).

Различай три события: изменение владельца ресурса, создание нового объекта-обёртки и уничтожение старого объекта-обёртки. Перемещение не завершает автоматически жизнь исходной обёртки. Её деструктор всё ещё будет вызван в обычном порядке.

У большинства типов стандартной библиотеки состояние после перемещения корректно, но не определено точнее, если для конкретного типа нет дополнительной гарантии. Нельзя автоматически считать перемещённую строку пустой. Для пользовательского типа поведение определяется его собственным контрактом; язык не создаёт за автора безопасную семантику произвольно написанного move-конструктора. Источник: [Moved-from state of library types — `[lib.types.movedfrom]`](https://timsong-cpp.github.io/cppwp/n4861/lib.types.movedfrom).

У move-only класса обычно удаляют копирующие операции, а перемещающие либо пишут, либо явно default-ят, если поведение членов подходит. Пользовательское объявление деструктора влияет на автоматическое объявление перемещающих операций. Не предполагай, что любое наличие `unique_ptr`-члена автоматически создаст нужный публичный интерфейс окружающего класса. Правила: [Copy/move constructors — `[class.copy.ctor]`](https://timsong-cpp.github.io/cppwp/n4861/class.copy.ctor).

Аргумент ссылочного типа ещё не означает передачу владения: вызываемая функция может отказаться от работы, ничего не создавая. Но вычисления аргументов уже произошли до входа в её тело. Например, вызов фабрики в `accept(make_resource())` выполняется даже тогда, когда `accept` затем сразу отказывается принимать результат. Не смешивай это с `accept(std::move(existing))`: само приведение ресурса не забирает. Источник порядка вызова: [Function call — `[expr.call]`, p7–8](https://timsong-cpp.github.io/cppwp/n4861/expr.call#7).

## 8. Создание объекта, присваивание и уничтожение

Эти операции имеют разные исходные условия:

| Операция | Что было до неё | Что она означает |
|---|---|---|
| Конструирование | ещё нет полностью созданного целевого объекта | инициализация нового объекта |
| Присваивание | целевой объект уже существует | изменение существующего объекта |
| Уничтожение | объект существует | завершение его жизни и работа деструктора |

```cpp
#include <string>
#include <utility>

std::string first("hello");         // обычное конструирование
std::string second(first);          // копирующее конструирование
std::string third(std::move(first)); // перемещающее конструирование
second = std::move(third);          // перемещающее присваивание
```

Копирующий конструктор не заменяет оператор присваивания и наоборот. Наличие конструктора из аргументов не означает наличия конструктора по умолчанию. Объявление `U item;` для классового `U` пытается вызвать его конструктор по умолчанию; это уже создание объекта, а не резервирование пустой ячейки. См. [Initializers — `[dcl.init]`](https://timsong-cpp.github.io/cppwp/n4861/dcl.init).

Указатель на память и выражение присваивания сами не дают общего способа создать произвольный нетривиальный объект в этой памяти. В особенности это не способ обойти отсутствие нужного конструктора или управление ресурсами класса.

## 9. Хранилище и время жизни объекта

**Хранилище** — область памяти нужного размера и выравнивания. **Время жизни объекта** — период, когда в ней существует определённый объект с применимыми к нему правилами языка. Это разные уровни.

Для обычного нетривиального класса важно завершение инициализации: одного получения байтов недостаточно для использования такого объекта как полностью созданного. У классового объекта lifetime заканчивается с началом вызова деструктора; освобождение или соответствующее переиспользование памяти тоже может завершать lifetime. Правила поведения во время самого конструктора и деструктора оговорены отдельно. См. [Lifetime — `[basic.life]`, p1–4](https://timsong-cpp.github.io/cppwp/n4861/basic.life#1).

После уничтожения объекта его прежние байты могут оставаться в памяти, а сама область может ещё принадлежать владельцу. Это не разрешает читать старый объект. И наоборот: уничтожение элемента не обязано освобождать память под область, пригодную для следующего элемента.

Для C++20 фраза «жизнь объекта всегда начинается только явным вызовом конструктора» слишком сильна: стандарт предусматривает неявное создание объектов некоторых implicit-lifetime типов определёнными операциями. Эти специальные правила не дают права трактовать произвольные байты как готовые `std::string` или `unique_ptr`. Источник: [Object model — `[intro.object]`, p10–13](https://timsong-cpp.github.io/cppwp/n4861/intro.object#10).

В учебной работе раздельное управление этими уровнями можно изучать через стандартные владеющие средства. Ручные `placement new`, `reinterpret_cast`, `std::launder` и арифметика сырых указателей не являются обязательной ступенью перед корректным управлением lifetime.

## 10. `std::optional<T>`: объект может отсутствовать

`std::optional<T>` из `<optional>` хранит состояние «значение есть / значения нет» и управляет временем жизни вложенного `T`. Сам optional может жить, пока вложенного объекта нет. Значение находится внутри памяти optional; библиотека не должна выделять для него отдельную динамическую память. Сам `T`, например строка, может выделять память для собственных ресурсов. Размер optional не обязан равняться `sizeof(T) + 1`: возможны выравнивание и иная служебная раскладка. У optional есть собственные требования к типу: в частности, служебные `std::in_place_t` и `std::nullopt_t` не могут быть его типом значения. Источник: [Class template optional — `[optional.optional]`, p1–3](https://timsong-cpp.github.io/cppwp/n4861/optional.optional#1).

### Пустота без default-конструктора `T`

```cpp
#include <optional>

struct AccessCode {
    explicit AccessCode(int number) : number(number) {}
    int number;
};

std::optional<AccessCode> code; // нет вложенного AccessCode
```

У `AccessCode` нет конструктора по умолчанию, но пустой optional создать можно. `std::nullopt` обозначает отсутствие значения; это не объект `AccessCode` с особым номером.

Optional не делает копируемым некопируемый `T`: копирование `optional<T>` зависит от копирования вложенного типа. См. [Constructors — `[optional.ctor]`](https://timsong-cpp.github.io/cppwp/n4861/optional.ctor).

### `emplace` и `reset`

```cpp
code.emplace(42); // создать вложенный AccessCode из аргумента int
code.reset();     // уничтожить его, оставить optional пустым
code.reset();     // для пустого optional нет вложенного объекта для уничтожения
```

`emplace(args...)` конструирует `T` непосредственно из аргументов; промежуточный `T` для этого не требуется. Если значение уже есть, сначала оно уничтожается. Поэтому повторный `emplace` — не присваивание и не операция с автоматическим сохранением прежнего значения при ошибке. Если новый конструктор бросил, optional остаётся без значения. Правила: [Assignment — `[optional.assign]`, перегрузки `emplace`](https://timsong-cpp.github.io/cppwp/n4861/optional.assign).

`reset()` уничтожает имеющееся значение и оставляет optional пустым; у пустого optional нет эффекта. Он объявлен `noexcept`. Источник: [Modifiers — `[optional.mod]`](https://timsong-cpp.github.io/cppwp/n4861/optional.mod).

Присваивания `optional<T>` могут требовать присваиваемости самого `T`, даже если во время конкретного вызова optional пуст. `emplace` требует конструирования, а не оператора присваивания. Не делай из наличия `emplace` вывод, что у типа есть все остальные операции optional.

### Доступ с проверкой и без неё

`has_value()` и проверка `if (code)` сообщают наличие значения. `*code` и `code->...` требуют, чтобы значение уже было: у пустого optional это нарушение предусловия и неопределённое поведение в рассматриваемом C++20. Они не обязаны бросать исключение. `code.value()` проверяет наличие и бросает `std::bad_optional_access`, если значения нет.

Для lvalue optional выражение `*code` даёт `T&`, а для константного lvalue — `const T&`. Доступ не создаёт копию. `auto copy = *code` и `auto& ref = *code` уже различаются: первое объявление создаёт отдельный объект, второе сохраняет ссылку. Источник: [Observers — `[optional.observe]`](https://timsong-cpp.github.io/cppwp/n4861/optional.observe).

### Перемещение optional и уничтожение — разные действия

После успешного перемещающего конструирования из непустого optional исходный optional **остаётся непустым**. Его вложенный объект жив, но находится в состоянии после перемещения. Это справедливо и для `optional<unique_ptr<int>>`: optional может содержать пустой `unique_ptr`. Для завершения жизни вложенного объекта нужна отдельная операция. Спецификация перемещающего конструктора optional зависит от `is_nothrow_move_constructible_v<T>`. Источник: [`[optional.ctor]`, p7–11](https://timsong-cpp.github.io/cppwp/n4861/optional.ctor#7).

Монадические операции `and_then`, `transform`, `or_else` не входят в используемый здесь интерфейс C++20. Этот материал на них не опирается.

## 11. Заимствованные ссылки и повторное использование памяти

Возвращённая ссылка обычно не владеет объектом и не продлевает его жизнь. У компонента, выдающего ссылку, должен быть явный контракт: какие действия оставляют её действительной, а какие инвалидируют.

Следует различать:

- уничтожение соответствующего объекта;
- перемещение объектов в другие адреса, например при перевыделении памяти;
- изменение значения живого объекта по прежнему адресу;
- появление другого объекта в той же области позднее.

Одинаковый адрес не доказывает, что старая ссылка по-прежнему допустима по контракту компонента. У C++ есть специальные правила прозрачной замены объектов, но они имеют условия и не отменяют ограничений конкретного интерфейса. В упражнении нельзя использовать старую ссылку после её инвалидирования, даже если та же ячейка уже занята новым значением. Общее основание: [Lifetime — `[basic.life]`, p6–8](https://timsong-cpp.github.io/cppwp/n4861/basic.life#6); конкретные правила контейнера задаёт условие упражнения.

Проверка адреса или чтение «на пробу» не проверяет допустимость ссылки. Само чтение уже может нарушать правила. Рассуждать нужно о событии окончания lifetime и контракте владельца.

## 12. Фиксированное хранилище и цена выделения памяти

Фиксированная вместимость во время выполнения и размер, известный во время компиляции, — разные вещи. Вместимость может определяться аргументом конструктора, но затем оставаться неизменной.

Отдельно учитывают память инфраструктуры компонента и ресурсы каждого `T`. Отсутствие расширения инфраструктуры не означает, что `std::string` внутри элемента никогда не вызывает выделение памяти.

Для понимания стандартных средств полезно знать различие `size` и `capacity` у `vector`: `reserve(n)` резервирует место, не создавая новых элементов и не меняя `size`; `vector(n)` создаёт `n` элементов. После `reserve` нельзя индексировать элементы за пределами `size` так, будто они уже существуют. Эти примеры объясняют семантику средств библиотеки, а не выбирают внутреннее устройство упражнения. Правила: [`[vector.capacity]`](https://timsong-cpp.github.io/cppwp/n4861/vector.capacity), [`[vector.cons]`](https://timsong-cpp.github.io/cppwp/n4861/vector.cons).

Перевыделение памяти vector инвалидирует ссылки на его элементы. Поэтому стабильность ссылок требует анализа всех действий над хранилищем, а не только публичного названия операции. Само `reserve(n)` гарантирует вместимость **не меньше** запрошенной, а не ровно `n`; физический резерв вспомогательного средства и логический предел компонента могут быть разными понятиями. Источник: [`[vector.capacity]`, p3–7](https://timsong-cpp.github.io/cppwp/n4861/vector.capacity#3).

Стандартные требования сложности и количества операций не обещают конкретного времени в наносекундах. Практическая цена выделения памяти зависит от аллокатора, ОС, состояния памяти и реализации. Переиспользование хранилища уменьшает число причин обращаться к аллокатору; само по себе оно не доказывает жёсткую границу задержки.

## 13. Исключения и гарантии состояния

Исключение прерывает обычный путь управления. Для функции важно определить не только вид ошибки, но и допустимое состояние объектов после выхода с ней.

Обычно различают:

| Гарантия | Что обещается при исключении |
|---|---|
| Базовая | нет утечек, сохраняются инварианты, объект остаётся пригодным; значения могут измениться |
| Строгая | дополнительно нет наблюдаемого изменения защищаемого состояния операции |
| Небросающая | исключение не выходит из операции |

Область гарантии нужно называть. Конструктор пользовательского типа может вести журнал, менять внешний счётчик или обращаться к стороннему объекту. Строгая гарантия состояния контейнера не означает универсальный откат таких внешних эффектов. Терминология: [Microsoft Learn, How to: Design for exception safety, The three exception guarantees](https://learn.microsoft.com/en-us/cpp/cpp/how-to-design-for-exception-safety?view=msvc-170#the-three-exception-guarantees).

### Что происходит при неудачном конструировании

Если обычный неделегирующий конструктор объекта бросил, деструктор всего недостроенного объекта не вызывается. Но уже полностью построенные члены и базовые подобъекты уничтожаются. Автоматические локальные объекты при раскрутке стека тоже уничтожаются, если их создание завершилось. Поэтому ресурс, уже переданный корректному RAII-члену, может быть освобождён даже при неудаче внешнего конструктора.

Это не означает, что любое сырое выделение в теле автоматически защищено: у ресурса должен появиться владелец. Источник: [Constructors and destructors — `[except.ctor]`](https://timsong-cpp.github.io/cppwp/n4861/except.ctor).

Общий способ рассуждать о строгой гарантии — отделить потенциально бросающую подготовку от подтверждения нового состояния. На момент ошибки старое состояние должно оставаться описываемым, а временно приобретённые ресурсы — иметь владельца. Это принцип анализа, а не готовый порядок шагов для конкретных методов RingBuffer. Для собственной реализации потребуется проследить каждое место возможного исключения с учётом выбранного представления.

Обычный отказ по контракту и исключение из пользовательского конструктора несут разный смысл. Функция с результатом `bool` вполне может бросать; слово `try` в её имени не является частью семантики языка. Следуй контракту, а не предположению по названию.

## 14. `noexcept`: обещание функции и проверка выражения

### Спецификация

Объявление `void finish() noexcept;` обещает, что исключение не покинет функцию. Оно не требует от компилятора доказать отсутствие бросающих вызовов. Если исключение всё-таки выходит за эту границу, вызывается `std::terminate`. Поэтому приписать `noexcept` к ошибочному коду — не способ превратить его в безопасный. Источник: [Exception specifications — `[except.spec]`, p1–5](https://timsong-cpp.github.io/cppwp/n4861/except.spec#1).

Условная форма `noexcept(condition)` позволяет выразить зависимость от типов. Условие вычисляется при компиляции. Для обобщённой функции нужно учитывать не только её видимые операторы, но и выбранные конструкторы, присваивания, деструкторы, вспомогательные вызовы и создание результата. Утверждение «move обычно быстрый» не является доказательством отсутствия исключений.

### Оператор

`noexcept(expression)` внутри обычного выражения — оператор, возвращающий `bool` времени компиляции. Его аргумент не выполняется:

```cpp
#include <optional>
#include <type_traits>
#include <utility>

static_assert(noexcept(std::declval<std::optional<int>&>().reset()));
```

`declval` здесь нужен для записи выражения без реального объекта; его нельзя вызывать как обычную выполняемую функцию. Результат показывает статическую спецификацию, а не запуск операции с проверкой всех её внутренних путей. Правила оператора: [`[expr.unary.noexcept]`](https://timsong-cpp.github.io/cppwp/n4861/expr.unary.noexcept); назначение помощника: [`[declval]`](https://timsong-cpp.github.io/cppwp/n4861/declval).

### Возврат по значению тоже требует анализа

```cpp
#include <string>

std::string caption() {
    std::string result = "ready";
    return result;
}
```

Для такого локального объекта возможна NRVO: компилятор может построить его непосредственно в месте результата. В C++20 это разрешение, а не безусловная гарантия. Если устранения нет, правила возврата позволяют выбрать перемещение в подходящем случае. Не основывай корректность исключительно на наблюдении, что конкретная сборка устранила вызов. `return std::move(result);` также не является универсальным улучшением: такая форма не удовлетворяет обычному условию NRVO с именем локальной переменной. См. [Copy/move elision — `[class.copy.elision]`](https://timsong-cpp.github.io/cppwp/n4861/class.copy.elision).

Для собственного обоснования небросающей операции перечисляй используемые выражения и их требования. В частности, перемещающее конструирование и перемещающее присваивание имеют разные traits и могут иметь разные спецификации. В этом материале готовое доказательство `noexcept` для методов упражнения не приводится.

## 15. FIFO, циклическое переиспользование и сложность

FIFO означает, что среди ещё не извлечённых значений первым извлекают то, которое приняли раньше остальных. Это свойство логического порядка. Оно не требует, чтобы логически первый элемент всегда лежал в физическом начале памяти.

Циклическое переиспользование означает повторное использование конечного набора мест после освобождения. Можно представлять набор пронумерованных мест по кругу, но от этой картинки ещё не следуют ни способ описания состояния, ни формулы переходов. Их нужно вывести для своего представления. В задании политика переполнения — отказ; другие кольцевые структуры могут выбирать перезапись старых данных, поэтому одно название «ring buffer» не задаёт полный контракт.

Нулевая и единичная вместимости нужны для отдельного рассуждения: при нуле нет ни одного доступного места, а при единице физическое разнообразие положений минимально. Выражения с остатком от деления нельзя применять без учёта нулевого делителя. Наибольший интерес представляет сохранение смысла операций на границе, а не только на длинной обычной последовательности.

Инвариант — утверждение, описывающее допустимое состояние. Предусловие — то, что должно быть выполнено перед операцией; постусловие — её обещание после завершения. Исключительный выход может иметь отдельное постусловие. В собственном дизайне нужно связать представление с этими понятиями; готовые инварианты здесь намеренно не выбираются. Требования FIFO и граничного поведения определены [условием упражнения](../../exercises/03-ring-buffer/TASK.md).

### Что означает `O(1)`

Оценка должна называть переменную: `O(1)` по вместимости означает ограниченное сверху число действий управления, не растущее вместе с вместимостью. Это не обещание «одна машинная инструкция».

Если операция управления использует постоянное число действий, но вызывает копирование строки длины `L`, стоимость копирования нужно учитывать отдельно. Аналогично уничтожение объекта может освобождать его собственные ресурсы. Для обсуждения полезно записывать «стоимость управления + стоимость операций над `T`», не скрывая второе слагаемое.

`O(size)` вызовов деструктора описывает число уничтожений живых элементов. Оно само по себе не разрешает произвольный дополнительный обход всей вместимости при почти пустом контейнере. Следует отдельно считать действия управления и пользовательские операции. Оценка памяти `O(capacity)` допускает постоянный коэффициент и служебные поля; она не задаёт точный байтовый размер.

Требования конкретного упражнения к стоимости и владению приведены в [TASK.md](../../exercises/03-ring-buffer/TASK.md). Многопоточная публикация элементов, атомики и модели памяти в эту однопоточную задачу не входят; циклическая форма хранилища сама по себе не является механизмом синхронизации.
