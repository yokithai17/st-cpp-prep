# Теория для задания 02-lru-cache

Конспект исправлен 2026-10-12. Чтение объяснений ещё не подтверждает понимание: далее — квиз и самостоятельное обоснование архитектуры.

## 1. Указатель, ссылка и итератор

- **Указатель** — объект, который может хранить адрес другого объекта. Может быть `nullptr`, может быть переназначен. Размер зависит от платформы и типа указателя: 8 байт — распространённый размер указателя на объект на 64-битной платформе, но не общее правило C++.
- **Ссылка** — другое имя существующего объекта. После привязки её нельзя перепривязать: присваивание через ссылку меняет объект. Ссылка не является отдельным объектом; реализация может использовать адрес, но «обёртка над указателем» не описывает её семантику.
- **Итератор** — средство обхода последовательности. Итератор может быть указателем или объектом класса. Допустимые операции зависят от категории: у `vector` есть `it + n`, у `list` — последовательные `++` и `--`. `end()` обозначает позицию за последним элементом и не разыменовывается.

Ни ссылка, ни обычный указатель, ни итератор сами по себе не продлевают жизнь элемента контейнера. После уничтожения элемента сохранённый доступ становится недействительным.

## 2. Стоимость операций

Здесь n — число элементов. Стоимость операций над самими значениями (например, копирования строк) учитывается отдельно. O(1) не означает «одна машинная инструкция» и ничего не гарантирует о попадании в процессорный кеш.

### std::vector

| Операция | Сложность |
|---|---|
| `v[i]` | O(1); индекс должен быть в пределах размера |
| `v.at(i)` | O(1); проверяет границы |
| `push_back(x)` | амортизированное O(1), отдельная вставка — O(n) при реаллокации |
| `insert(pos, x)` | O(n) в худшем случае; без реаллокации — O(1 + расстояние от pos до конца) |
| `erase(pos)` | O(n) в худшем случае из-за сдвига последующих элементов |

Вставка в середину не обязательно вызывает реаллокацию: если места достаточно, элементы сдвигаются внутри текущего буфера. `reserve` может исключить реаллокацию для последующих вставок в пределах выделенной вместимости, но не устраняет сдвиги.

Элементы лежат подряд. Это обычно улучшает локальность при обходе по сравнению со списком, однако прогретый процессорный кеш не гарантирован.

Амортизированное O(1) для добавления в конец означает, что суммарная стоимость серии добавлений линейна по их количеству, хотя отдельные добавления дороги. Это отличается от среднего случая хеш-таблицы.

### std::list

| Операция | Сложность |
|---|---|
| `push_front(x)`, `push_back(x)` | O(1) |
| `insert(it, x)` | O(1), если позиция уже известна |
| `erase(it)` | O(1), если итератор на элемент уже известен |
| Поиск значения или переход к элементу по индексу | O(n) в худшем случае |
| `splice(pos, list, it)` для одного элемента | O(1) |

У списка нет `operator[]` или метода `get(i)`. Узлы не обязаны лежать подряд; обход может иметь хуже локальность. При оценке удаления по значению нельзя забывать стоимость поиска.

`splice` переносит существующий узел перед заданной позицией, в том числе внутри того же списка. Объект элемента не пересоздаётся; его итераторы, ссылки и указатели сохраняются. Перенос одного узла не бросает исключений. Для переноса между разными списками аллокаторы должны быть равны; исходный итератор должен быть разыменовываемым. У перегрузок для всего списка и диапазона другие условия — не переносим на них правила одного узла автоматически.

### std::unordered_map

| Операция | Средняя сложность | Худшая сложность |
|---|---|---|
| `find(key)` | O(1) | O(n) |
| `insert({key, value})`, `emplace(key, value)` | O(1) | O(n) |
| `erase(key)` | O(1) | O(n) |

Хеш помогает выбрать бакет; при коллизиях требуется сравнивать ключи. Конкретная схема узлов и выбора бакета — деталь реализации, не контракт C++. Плохие коллизии ухудшают сложность; расположение узлов может ухудшать локальность.

`operator[]` вставляет отсутствующий ключ со значением по умолчанию. Для поиска без вставки подходит `find`.

## 3. Инвалидирование

### std::vector

- При вставке реаллокация нужна, если **новый размер превысил бы прежнюю вместимость**. После операции `size() <= capacity()`; состояние `size() > capacity()` не является нормальным состоянием вектора.
- С реаллокацией теряют действительность все указатели, ссылки и итераторы на элементы, а также прежний `end()`.
- Без реаллокации при вставке сохраняется доступ к элементам **до** позиции вставки; на позиции вставки и после неё указатели, ссылки и итераторы инвалидируются. Прежний `end()` тоже инвалидируется.
- При `erase` доступ на позиции удаления и после неё инвалидируется; к предшествующим элементам сохраняется.
- `reserve` инвалидирует доступ, если вызвал реаллокацию.

### std::list

Вставка сохраняет указатели, ссылки и итераторы на существующие элементы. Удаление инвалидирует доступ только к удалённым элементам. `splice` одного узла сохраняет доступ к этому узлу и остальным элементам.

### std::unordered_map

Rehash инвалидирует итераторы, но сохраняет указатели и ссылки на элементы. Это гарантия стандартной библиотеки, независимая от GCC.

Вставка может вызвать rehash. Без него итераторы сохраняются; указатели и ссылки на существующие элементы сохраняются в обоих случаях. При вставке `k` элементов итераторы гарантированно сохраняются, если `size_before + k <= max_load_factor() * bucket_count()`.

`erase` инвалидирует доступ только к удалённому элементу. `clear` и уничтожение контейнера уничтожают все его элементы.

## 4. Примеры

Фрагменты предполагают подключение соответствующих заголовков и выполняются независимо.

```cpp
std::vector<int> a = {1, 2, 3};
a.reserve(10);
int& x = a[1];
int* p = &a[0];
a.insert(a.begin() + 1, 5); // insert принимает итератор, не индекс
// Реаллокации нет, но x инвалидирована: она была на позиции вставки.
// Не читаем x. p остаётся действительным, *p == 1.
```

```cpp
std::list<int> lst = {1};
auto it = lst.begin();
lst.push_front(2);
// it по-прежнему обозначает элемент со значением 1.
lst.splice(lst.begin(), lst, it);
// it всё ещё действителен; теперь этот узел первый.
lst.erase(it);
// it инвалидирован; не разыменовываем его.
```

```cpp
std::unordered_map<int, std::string> m = {{1, "A"}};
auto it = m.find(1);
const std::string* p = &it->second;
m.rehash(m.bucket_count() + 100);
// it больше не используем. p действителен, *p == "A".
m.erase(1);
// p теперь недействителен; не разыменовываем его.
```

## 5. Владение и lifetime в задании

Кеш владеет строками, а `get` возвращает заимствованный `const std::string*`. `const` запрещает изменение строки через этот указатель, но кеш может изменить её сам.

- Успешный `get` обновляет порядок; чтение через ранее полученный указатель — нет.
- Вставки и удаления других ключей сохраняют указатель, пока его запись не вытеснена.
- `put` того же ключа должен сохранить **объект строки**, чтобы старый указатель показывал новое значение.
- Удаление или вытеснение записи и уничтожение кеша инвалидируют указатель. Повторная вставка того же ключа его не восстанавливает.
- Указатель на объект `std::string` и указатель на символы из `c_str()` имеют разные гарантии. Изменение строки может инвалидировать указатель на символы.

## 6. Инварианты и исключения

Инвариант — условие согласованности состояния, которое должно выполняться на границах операций. Для нескольких структур мало проверить каждую отдельно: важна правильность связей между ними.

До реализации нужно сформулировать, как проверяются уникальность ключей, соответствие записей в структурах, правильность порядка и ограничение размера. Любая сохранённая связь должна вести к живому объекту.

Вставка узла и расширение таблицы могут требовать выделения памяти. Создание или копирование строки также может бросить исключение; копирование аргумента `put` может произойти ещё до входа в метод.

- **Базовая гарантия:** после исключения нет утечек, инварианты соблюдены, объект пригоден для использования; прежние данные могут измениться.
- **Сильная гарантия:** при исключении наблюдаемое состояние остаётся прежним.
- **Гарантия отсутствия исключений:** операция не бросает.

В задании достаточно базовой гарантии для `put`, включая ограничение размера. Если одна структура уже изменена, а изменение второй бросило исключение, нужно восстановить согласованность. RAII освобождает ресурсы, но само по себе не исправляет связь двух контейнеров. Точный порядок действий и восстановление студент обосновывает для своей архитектуры.

## 7. Требования к сложности кеша

`get`, `put`, `erase` — ожидаемое O(1) по числу записей; `size`, `capacity` — O(1). Стоимость строк учитывается отдельно: копирование строки длины L — O(L). Память служебных структур — O(capacity), дополнительно хранится память строк. Худшую сложность выбранных контейнеров нужно указать в README.
