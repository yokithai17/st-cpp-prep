## 3. Карта знаний и глубина освоения

«Умею» означает: объясняю идею, пишу небольшой пример без подсказок, знаю ограничения и могу проверить поведение. «Знаком» означает: понимаю назначение и могу продолжить изучение по документации.

### 3.1. C++ — обязательное ядро

- Типы, const, ссылки, указатели, области видимости, преобразования типов, signed/unsigned, переполнение и undefined behavior.
- Время жизни объекта и время жизни памяти; dangling pointers/references/views; владение ресурсом.
- RAII; rule of zero/five; copy/move constructors и assignment; copy elision; деструктор и noexcept; базовая и сильная гарантия исключений.
- Value categories: lvalue/xvalue/prvalue; `std::move` как преобразование, forwarding references и `std::forward`; почему перемещение const-объекта может приводить к копированию.
- `unique_ptr`, `shared_ptr`, `weak_ptr`: владение, циклы, счётчик ссылок, стоимость; потокобезопасность control block не делает объект под указателем потокобезопасным.
- STL: `vector`, `array`, `deque`, `list`, `map`, `unordered_map`, `set`, `priority_queue`; итераторы, инвалидирование, сложность операций, reserve/resize, reallocation и локальность.
- `string`, `string_view`, `span`, `optional`, `variant`, `visit`, `any`; ownership и ограничения views.
- Лямбды, захваты, dangling capture; виртуальные функции и деструктор, slicing; композиция и полиморфизм; type erasure на небольшом примере.
- Шаблоны: deduction, overload resolution, specialization, SFINAE, `enable_if`, `if constexpr`; в C++20 — concepts/requires и стандартные iterator concepts.
- Компиляция и линковка, translation units, headers, ODR, static/shared libraries. Отличать языковую гарантию от деталей ABI и реализации библиотеки.

Рабочий стандарт проектов — C++20; нужно понимать базу C++17 и уметь объяснить используемые расширения C++20. Из C++23 познакомиться с полезными возможностями, например `expected`, с учётом поддержки компилятора. Coroutines и modules не должны вытеснять ядро.

Контроль: реализовать RAII-wrapper для файлового дескриптора, LRU-cache и ограниченный шаблонный интерфейс; найти ошибку времени жизни; объяснить выбор контейнера и стоимость копирования.

### 3.2. Алгоритмы и структуры данных

- Асимптотика времени и памяти; амортизированная сложность; ожидаемая и худшая сложность хеш-таблицы.
- Массивы и строки, сортировка, бинарный поиск и поиск по ответу, prefix sums, two pointers, sliding window.
- Хеширование, heaps, stack, queue, monotonic stack/queue.
- DFS/BFS, деревья, DSU, топологическая сортировка, Dijkstra при неотрицательных весах.
- Базовое динамическое программирование, greedy с доказательством, интервалы, битовые операции.
- Fenwick/segment tree и более сложные графовые задачи — после уверенного ядра, если диагностика и контесты показывают необходимость.

Плановый ориентир — 140–180 тщательно разобранных новых задач и 35–50 повторных решений. Число задач не является пропускным баллом. Начать с CSES; Codeforces — для незнакомых задач и работы под таймером. При достаточной базе постепенно добавить задачи рейтинга 1600–1800 как учебное усложнение; официальный рейтинговый порог Spectral не подтверждён.

Каждое решение: уточнить условие → простой подход → оптимизация → инвариант/доказательство → оценка времени и памяти → код → крайние случаи. Повторение через 7 и 30 дней. Если нет идеи за 25–35 минут, разобрать решение, записать недостающий приём и затем решить заново без текста. Не считать чтение редакториала самостоятельным решением.

Контроль: незнакомая задача средней сложности за 35–45 минут с ясным объяснением и проверкой; две задачи за 75–90 минут в учебном контесте. Это наш ориентир, а не заявленный регламент компании.

### 3.3. АКОС, CPU и Linux

- Представление чисел и байтов, endianness, размер/выравнивание/padding; floating point, fixed point.
- Стек вызовов, регистры и calling convention; чтение простого x86-64 assembler; работа с дизассемблированием.
- CPU caches и cache lines, locality, prefetching, branch prediction, pipelining/out-of-order execution на уровне причин задержки.
- Virtual memory, pages, page faults, TLB; heap/stack; процесс и поток; context switches и scheduler.
- System calls, file descriptors, файлы, sockets, mmap; основы ELF и линковки.
- Практика: shell, Git, gdb/lldb, core dumps, strace, perf, objdump. В virtual machine/WSL аппаратные counters могут быть недоступны: тогда используем доступное профилирование и фиксируем ограничение.

Контроль: найти segfault в gdb, показать путь чтения файла в strace, назвать hot function по профилю, связать простой цикл C++ с инструкциями и объяснить разницу между contiguous storage и pointer chasing.

### 3.4. Конкурентность

- `thread`/`jthread`, mutex, scoped locks, condition_variable с предикатом; корректное завершение потоков.
- Race condition и data race; deadlock/livelock; false sharing и true sharing.
- Atomic operations и compare_exchange; C++ memory model: sequenced-before, synchronizes-with, happens-before; acquire/release/relaxed/seq_cst.
- Почему `volatile` не заменяет синхронизацию; почему атомарность отдельного счётчика не делает составную структуру безопасной.
- Producer/consumer, bounded queue, backpressure; ownership между потоками; lost wakeup и spurious wakeup.
- Сначала очередь под mutex, затем SPSC ring buffer. Прогресс lock-free/wait-free изучать с оговорками о платформе и используемых atomic; не называть любую очередь с atomic lock-free автоматически.

Контроль: реализовать ограниченную блокирующую очередь и SPSC; нарисовать связь публикации данных через release/acquire; объяснить, когда mutex выгоднее spinning. Учебный mutex строить только с явно заданной семантикой wait/wake, проверкой состояния перед засыпанием и повторной проверкой после пробуждения.

ThreadSanitizer полезен для поиска гонок [R9], но отсутствие отчёта не доказывает корректность memory ordering. Нужны аргумент корректности и тесты.

### 3.5. Сети и поток данных

- TCP как поток байтов и UDP как датаграммы; TCP connection lifecycle, framing, partial read/write, EOF, таймауты и ошибки.
- Sockets, blocking/non-blocking IO, select/poll и Linux epoll на практическом уровне.
- Byte order и безопасное декодирование, версии протокола, validation длины и диапазонов.
- Sequence numbers, duplicates, out-of-order events, gaps; snapshot + incremental updates; recovery и reconnect.
- Throughput, latency, queueing и backpressure; burst traffic, drop policy и ограничение памяти.

Контроль: написать TCP-передачу с length-prefixed frames, UDP-generator/receiver, обработать обрезанный пакет и пропущенное сообщение; объяснить поведение перегруженного consumer.

### 3.6. Предметная область и инженерия

Для проектов: bid/ask, spread, best bid/offer, market/limit order, price level, order ID, order book, tick size, snapshot и delta. Отличать market-by-price (L2, объёмы на уровнях) от market-by-order (L3, отдельные заявки). Из L2 нельзя восстановить очередь отдельных заявок. Различать книгу, принимающую биржевые события, и matching engine, который сам сопоставляет заявки.

Поддерживающие навыки: CMake/CTest, GoogleTest или Catch2, форматирование, clang-tidy, CI, sanitizers, понятные pull requests и README. Python — генераторы, эталонная модель и анализ CSV, достаточно одного небольшого набора скриптов. Английский — техническая документация и 5–10 минут устного рассказа о проекте. Математическая база МКН помогает доказывать инварианты; дополнительные ML-проекты оставляем необязательными для этой C++ цели.

Пример: понедельник 1,5 ч теории; вторник 1 ч задач; среда 1,5 ч теории; четверг 1 ч задач; суббота 3 ч проекта; воскресенье 1,5 ч проекта + 1 ч устных вопросов + 0,5 ч обзора/английского. На неделе с полноценным моком его время берём из блока проекта и устной практики.

На сессии: 2 ч повторения, 1–2 ч поддержания проекта, 1 ч задач. Один результат в неделю сохраняет ритм. После сессии не накапливать «долг» часов. При перегрузке сокращать необязательные фичи, а не тестирование и восстановление базовых знаний.

Режимы адаптации: при 6–8 ч/нед. оставить два репозитория, включив лабораторию в основную работу; отказаться от живой биржи, pool allocator и сложных алгоритмов. При 14–16 ч/нед. добавить внешнее ревью, дополнительный контест и небольшой вклад в open-source. Базовая программа остаётся прежней.

## 6. Пет-проекты

Основные работы: `cpp-performance-lab`, `cpp-orderbook-replay`, `cpp-feed-handler`. Код книги из второго проекта подключаем как библиотеку в третий. Это наша учебная архитектура, а не предположение о внутренней системе Spectral.

### Проект 1. cpp-performance-lab

Срок: месяцы 2–3, расширение в месяце 10. Бюджет: около 30–40 часов.

Цель — научиться ставить проверяемый эксперимент и объяснять стоимость решения. Минимум: LRU-cache с простой спецификацией, набор функциональных тестов, microbenchmarks и отчёт по результатам.

Последовательность:

1. Корректный LRU: ключ, значение, capacity, get/put/erase; ожидаемая O(1) через hash table + список. Определить поведение capacity=0, повторного put и возвращаемого значения после eviction.
2. Измерить стоимость копирования больших значений и варианты владения. Объяснить время жизни и стоимость shared ownership.
3. Три исследования: последовательный обход vector/list при сопоставимых данных; парсинг чисел общим и ограниченным по формату методом; false sharing у независимых счётчиков с вариантом выравнивания.
4. Проверить, что результаты реально используются и компилятор не удаляет работу; зафиксировать размер данных, настройки и повторения.
5. Сохранить CSV, команды запуска и 2–3 страницы выводов, включая случаи отсутствия ускорения.

Не утверждать, что один контейнер всегда быстрее другого. В опыте false sharing использовать независимые атомарные счётчики или корректно разделённые объекты: эксперимент с data race не является допустимой baseline. Показания wall clock и профиля должны объяснять наблюдаемую разницу.

Готовность: тесты LRU проходят, lifetime выдаваемых значений описан, другой человек может повторить эксперимент, есть объяснение хотя бы одного эффекта на уровне памяти/CPU.

### Проект 2. cpp-orderbook-replay

Срок: месяцы 4–6. Бюджет: около 60–80 часов.

Цель — реализовать детерминированную модель книги по синтетическим событиям L3. Для первой версии достаточно add/cancel/execute, order ID, instrument ID, side, integer price ticks, quantity и sequence number. Это книга, применяющая входные события, а не полный matching engine.

Последовательность:

1. Написать спецификацию: уникальность ID, обработка неизвестного cancel/execute, запрет отрицательного остатка, overflow, порядок sequence и поведение при malformed event.
2. Сделать медленную эталонную модель на Python. На каждом шаге сравнивать нормализованное состояние со C++ реализацией.
3. C++ baseline: ordered price levels, индекс по order ID, поддержка best bid/ask и объёма уровня. Не поддерживать FIFO, если интерфейс проекта его не использует; если добавлен matching, явно добавить price-time priority.
4. CLI replay: прочитать журнал событий, применить, выдать статистику и deterministic digest нормализованного состояния. Порядок unordered containers не должен менять вывод.
5. Сгенерировать валидные случайные сценарии и отдельные невалидные. Добавить граничные тесты, fixed seed и уменьшение найденного контрпримера вручную или скриптом.
6. Снять профиль и baseline; изменить одну выбранную структуру данных только после обнаружения узкого места.

Инварианты: один ID обозначает не более одной активной заявки; остаток неотрицателен; агрегированный объём уровня равен сумме его заявок; удалённые/нулевые уровни не остаются best price; одинаковая последовательность событий даёт одинаковый результат. В учебном continuous-book генераторе отдельно определить допустимость crossed book и правила его устранения, а не объявлять это универсальным правилом любых рыночных данных.

Готовность: ручные сценарии и минимум десятки случайных seeds дают одинаковое состояние с эталоном; есть тесты пустой книги, частичного исполнения, duplicate IDs и некорректных quantity; release содержит инструкции и честный performance report.

### Проект 3. cpp-feed-handler

Срок: месяцы 7–11. Бюджет: около 90–110 часов. Основной проект портфолио.

Цель — получить данные, декодировать их, контролировать целостность потока, передать в книгу и измерить задержки. Основной воспроизводимый режим работает полностью локально, независимо от внешнего API.

Архитектура: generator/replay source → socket receiver → decoder + validation → sequence/recovery → bounded queue → book updater → metrics и журнал.

Последовательность:

1. Локальный TCP-generator и receiver; length-prefixed framing, ограничение размера, partial reads/writes и EOF. Собственный небольшой протокол с версией и документированным byte order.
2. Добавить UDP-вариант источника: sequence numbers, контроль длины, дубликаты и перестановку. Нельзя трактовать wire buffer как произвольную C++ struct без проверки alignment/layout/endianness.
3. Передать события в модель L3 из проекта 2. Отдельный thread получает/декодирует, другой применяет события; bounded queue под mutex, корректный shutdown.
4. Fault injection: пропуски, duplicates, reorder, truncated frame, неверная длина, slow consumer, переполнение очереди, disconnect/reconnect и snapshot recovery.
5. State machine: live → invalid/recovering → snapshot applied → live. При gap или потере необходимых delta старую книгу не выдаём как актуальную. Ограничить буфер восстановления; определить, какие delta можно применять после snapshot sequence.
6. Baseline latency/throughput; отдельно затраты decoder, queue, book; контролируемая подача событий и burst нагрузки.
7. После измерений — SPSC, preallocation и другой layout по одной оптимизации за раз. Сравнить с однопоточным режимом: дополнительный поток может ухудшать latency.
8. Длительный прогон, ограничение памяти, счётчики ошибок/пропусков, README, CI и отчёт.

Необязательное расширение: read-only adapter к публичному рыночному feed по актуальной документации выбранной биржи. Если источник предоставляет только L2, нужен отдельный MBP book с обновлениями уровней; он не является восстановлением L3-заявок. Live adapter не должен заменять deterministic offline tests и не входит в обязательный объём.

Готовность: рабочий end-to-end запуск; корректное обнаружение gaps; восстановление проверяется относительно эталона; нет бесконечного роста буфера; exit не зависает; санитайзеры не выявляют ошибок в проверенных сценариях; результаты измерений воспроизводимы.

### Общий стандарт завершённого проекта

- README на английском или двуязычный: задача, архитектура, build/test/run, ограничения, выбранные trade-offs и данные измерений.
- CMake, CTest, выбранный тестовый фреймворк; Debug с диагностикой и отдельный Release для измерений.
- Git-история с понятными изменениями; issues/milestones; небольшие pull requests даже при самостоятельной работе.
- Сценарии negative tests, differential tests там, где есть эталон, и stress tests для очередей/потоков.
- CI; ASan/UBSan и отдельная конфигурация TSan для конкурентного кода. Санитайзеры не включать в результаты performance baseline.
- Данные и скрипт воспроизведения; зафиксированный seed; changelog релиза.
- 5-минутное демо и 10-минутная защита: почему эти структуры, где bottleneck, что сломалось и как найдено, какие альтернативы отвергнуты.

Необязательные темы при оставшемся времени: pool allocator, `pmr`, mmap replay, небольшой matching engine. DPDK, kernel bypass, FPGA, сложные MPMC-очереди и собственная lock-free memory reclamation — за пределами обязательного плана.

## 7. Как измеряем производительность

1. Сначала корректность и baseline. Любая оптимизация сохраняет функциональные проверки.
2. Записать CPU, ОС, compiler/version, flags, commit, dataset/seed, число потоков, affinity если применялась и доступность hardware counters.
3. Отделить microbenchmark от pipeline benchmark. В latency interval явно указать начало и конец: decoder-only, enqueue-to-consume или ingress-to-book-update.
4. Вывести throughput и p50/p95/p99; p99.9 — если достаточно samples. Для 1 млн событий p99.9 описывается примерно тысячей самых медленных наблюдений; даже это не отменяет повторных прогонов и контроля нагрузки.
5. Для односторонней задержки в локальном тесте использовать один совместимый монотонный clock domain. Нельзя просто вычесть timestamp биржи или генератора на другой машине без решения задачи синхронизации часов.
6. Прогреть программу, убрать Debug и diagnostics instrumentation из measured run, измерить overhead timestamping; повторить 5–10 раз и хранить raw results. Не усреднять перцентили как будто это перцентиль объединённой выборки.
7. Для сравнения очередей зафиксировать одинаковые capacity, payload, workload и политику переполнения. Отличать стоимость queue operation от полного pipeline.
8. Подача событий — с заданным расписанием/rate и burst режимом, а не только «новое событие после обработки предыдущего». Иначе тест может скрывать queueing задержки (coordinated omission).
9. Отдельно публиковать drops, длину очереди, invalid/recovery episodes и ресурсные затраты. Ускорение ценой необъявленной потери сообщений нельзя выдавать за улучшение того же сервиса.
10. Не задавать домашнему компьютеру произвольную норму «меньше микросекунды». Критерий — понятное измерение и обоснованное сравнение на одном окружении.

Пример строки результата: commit, build flags, workload, samples, throughput, p50, p99, drops, max_queue_depth, repeated_run_id. Все численные достижения в CV берём только из реального отчёта.

## 9. Наши пробные интервью

С первого месяца — 15–20 минут устных вопросов еженедельно. С месяца 2 — полноценный мок раз в 4–6 недель. За последние 6–8 недель — примерно раз в неделю, с обязательным разбором ошибок. Плановый итог — 8–12 полных моков; важнее закрывать слабые места, чем считать сессии.

### Мок A: C++ и структуры данных, 75 минут

5 мин — рассказ о себе; 15 мин — lifetime/RAII/move/views; 35 мин — новый вариант кеша или задачи на контейнеры; 10 мин — exceptions/edge cases; 10 мин — обратная связь.

Задание: кеш фиксированной ёмкости с get/put/erase; заранее оговорить работу с большими объектами и lifetime возвращаемых значений. Follow-up: что изменится при concurrent reads, почему const-объект не решает lifetime, когда shared_ptr оправдан.

### Мок B: системы и concurrency, 90 минут

10 мин — CPU/cache/VM; 20 мин — review небольшого pipeline; 35 мин — bounded blocking queue и shutdown; 15 мин — acquire/release, backpressure и false sharing; 10 мин — feedback.

Follow-up: consumer медленнее producer; один поток завершился; wait проснулся без данных; счётчики располагаются рядом; кто владеет буфером сообщения. Не просить SPSC раньше освоения mutex/CV и memory model.

### Мок C: сети и проект, 90 минут

5 мин — уточнение входных условий; 20 мин — TCP framing или decoder; 25 мин — sketch feed pipeline; 20 мин — gap/snapshot/recovery и overload; 10 мин — защита измерений; 10 мин — feedback.

Follow-up: timestamp другого хоста, fragmented read, malformed length, gap при переполнении очереди, ограничение recovery buffer, p99 ухудшился при росте throughput.

### Мок D: алгоритмический, 75–90 минут

Две незнакомые задачи с кодом C++ и объяснением. Интервьюер оценивает требования, идею, доказательство, сложность, качество кода, тесты и коммуникацию. Повторные решения опубликованных задач не заменяют новые.

### Итоговая шкала

Для каждой области C++, алгоритмы, системы, конкурентность/сети и коммуникация выставляем 0–4: 0 — отсутствует понимание; 1 — фрагменты; 2 — решение со значимой помощью; 3 — самостоятельное правильное решение; 4 — правильное решение с обсуждением альтернатив и ограничений.

Рабочий ориентир: минимум 3 по ключевым областям на двух независимых итоговых моках. Это наша учебная шкала, не проходной балл Spectral. Ошибки времени жизни, необоснованная потокобезопасность, потерянные wakeups и выдуманные benchmark results исправляем до подачи проекта как завершённого.

Внешний интервьюер: однокурсник для алгоритмов, преподаватель/ассистент или разработчик с системным C++ опытом для проектов и concurrency. Хотя бы один поздний мок желательно проводить с человеком, который ранее не видел код. Сессии с ChatGPT полезны для вопросов/доказательств/разбора, но не заменяют внешнего исполнения и ревью программы.

## 11. Контроль прогресса и портфолио

Каждые четыре недели записать: освоенные темы; ссылку на работающий результат; число самостоятельно решённых и повторных задач; три главные ошибки; один следующий эксперимент. Отдельно вести журнал ошибок интервью: вопрос → мой ответ → причина ошибки → контрпример → исправленный ответ → дата повторения.

Контрольные точки:

- Конец месяца 3: корректный LRU, RAII, templates, первый lab release; способность объяснять язык через lifetime и стоимость.
- Конец месяца 6: рабочий deterministic book, эталон и очередь; понятное владение между потоками.
- Конец месяца 9: feed pipeline с recovery, baseline и fault tests.
- Конец месяца 11: завершённые release, README, отчёты, CV и внешнее ревью.
- Конец года: два стабильных итоговых мока, новые coding задачи, уверенная защита одного проекта и подготовленные отклики на подходящие роли.

Если контроль не пройден, добавить 1–2 недели на конкретный пробел и убрать необязательную фичу. При слабых алгоритмах перенести час проекта на задачи; при слабом C++ — час задач на примеры lifetime/templates; при отсутствии готового проекта — сократить широту чтения и закрыть MVP.

Финальный GitHub: 2–3 закреплённых проекта; ссылки на releases и benchmark reports; одно ясное описание вклада. В CV на одну страницу: обучение, C++/Linux/tools, 2–3 проекта с проверяемыми результатами, релевантные соревнования и английский. Не приписывать пет-проектам коммерческий опыт.

Пример формулировки с незаполненными числами: «Реализовал C++20 Feed Handler с UDP/TCP ingestion, bounded queue и snapshot recovery. Проверил корректность через эталон и fault injection; после [конкретное изменение] p99 снизилась с [измерение] до [измерение] при [workload] на [CPU]». Заполнять только после собственного измерения; если улучшения нет, описать обнаруженный bottleneck и ограничения.

## 12. Первые две недели

### Неделя 1: диагностика и окружение

1. Проверить C++: объяснить lifetime `string_view`, reserve/resize, move const-объекта, invalidation итератора и copy/move owning класса. На каждый ответ — маленький кодовый пример.
2. За 75–90 минут решить две ранее незнакомые задачи: одна на массив/строку/поиск и одна на BFS или структуру данных. Записать места остановки.
3. Linux + GCC/Clang, Git, CMake, debugger, выбранный test framework. Конкретную ОС/IDE выбрать по имеющемуся компьютеру; специальное железо не требуется.
4. Мини-проект: RAII-wrapper для file descriptor, запрет copy, корректный move, тесты закрытия/перемещения и ошибки открытия.
5. Включить warnings и ASan/UBSan в диагностической сборке; найти одну заранее внесённую ошибку в debugger.

Пример диагностического запуска после появления исходника: `clang++ -std=c++20 -Wall -Wextra -Wpedantic -g -O1 -fsanitize=address,undefined main.cpp`. Для измерений — отдельная Release сборка без sanitizer. Эта команда — ориентир конфигурации, исходный код проекта ещё не создан данным планом.

### Неделя 2: первый самостоятельный компонент

1. Определить интерфейс LRU и контракты операций.
2. Реализовать baseline и тесты пустого/полного кеша, eviction, повторного put, erase и missing key.
3. Разобрать container choice, время жизни результата и исключения на вставке.
4. Начать журнал ошибок и решить 2–3 новые задачи.
5. Провести 20-минутный мини-мок: защита LRU и три вопроса о владении.

После диагностики уточнить фактическое количество часов в неделю и уже пройденные университетские курсы. Это корректирует темп и глубину первых блоков; исследование компании и проекты сохраняют смысл.
